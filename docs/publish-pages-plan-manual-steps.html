Publish Pages Verification

These are the checks that only a person with real infrastructure can do for feature/publish-pages of html-artifact-deploy. Do them after the last phase merges and before the pull request merges, and paste each item's report line into the PR. Your ticks are saved in this browser only.

Throughout, replace example.com with your own domain, publish.example.com with the server's host name, and pages.example.com with the pages host name.

Before implementation

Nothing. Every phase builds and tests against fakes: a stubbed Google client, a temporary pages folder and an in-process HTTP client.

After implementation

ma1 · Google OAuth client and an Ubuntu server

Time about 90 minutesNeeds a Google Workspace admin or project owner, an Ubuntu 24.04 machine with a public IP, DNS for your domain

The full guide is docs/deployment.md on feature/publish-pages. These steps follow it.

  1. At your DNS provider, add A (and AAAA, if the server has IPv6) records for publish.example.com and pages.example.com, both pointing at the server.

    dig +short publish.example.com and dig +short pages.example.com both print the server's address.

  2. Open Google Cloud → New project. Create a project named html-artifact-deploy, or pick an existing one.
  3. Open Google Auth Platform → Branding. Set the app name to html-artifact-deploy, then save. Under Audience, choose Internal so only your Workspace accounts can sign in.
  4. Open Clients → Create client. For Application type choose Web application, and name it html-artifact-deploy. Under Authorized redirect URIs, add https://publish.example.com/oauth/google/callback, then click Create.

    A dialog with a Client ID ending in .apps.googleusercontent.com, and a Client secret.

    Keep the Client secret in that dialog, or download the JSON. It goes only into /etc/html-artifact-deploy/secrets.env on the server (step 9). Never put it in the config file, in chat, or in the PR.

  5. On the server, install Caddy from its apt repository by following Caddy's install steps for Ubuntu.

    systemctl status caddy shows active (running).

  6. Create the service account and the pages folder:
    sudo useradd --system --home-dir /var/lib/html-artifact-deploy --shell /usr/sbin/nologin html-artifact-deploy
sudo install -d -o html-artifact-deploy -g html-artifact-deploy -m 755 /srv/pages
  7. Install the feature branch into its own virtual environment:
    sudo apt install -y python3-venv git
sudo python3 -m venv /opt/html-artifact-deploy
sudo /opt/html-artifact-deploy/bin/pip install "git+https://github.com/andras-tkcs/html-artifact-deploy@feature/publish-pages"
  8. Copy deploy/config.example.toml to /etc/html-artifact-deploy/config.toml. Fill in pages.public_base_url, http.public_url, auth.google_client_id (the Client ID from step 4) and auth.allowed_domains (your Workspace domain). Keep the [fetch] section with allowed_hosts = ["raw.githubusercontent.com"], which ma2 uses. Then:
    sudo chown root:html-artifact-deploy /etc/html-artifact-deploy/config.toml
sudo chmod 640 /etc/html-artifact-deploy/config.toml
  9. Store the secret on the server only. Run sudo install -m 600 /dev/null /etc/html-artifact-deploy/secrets.env, then sudoedit /etc/html-artifact-deploy/secrets.env, and type one line: HTML_ARTIFACT_DEPLOY_GOOGLE_CLIENT_SECRET= followed by the Client secret from step 4.
  10. Check the configuration as the service account:
    sudo systemd-run --pty --wait --uid=html-artifact-deploy -p EnvironmentFile=/etc/html-artifact-deploy/secrets.env -p StateDirectory=html-artifact-deploy \
  /opt/html-artifact-deploy/bin/html-artifact-deploy --config /etc/html-artifact-deploy/config.toml check-config

    Configuration OK: /etc/html-artifact-deploy/config.toml

  11. Install and start the service with deploy/html-artifact-deploy.service:
    sudo curl -fsSL -o /etc/systemd/system/html-artifact-deploy.service \
  https://raw.githubusercontent.com/andras-tkcs/html-artifact-deploy/feature/publish-pages/deploy/html-artifact-deploy.service
sudo systemctl daemon-reload
sudo systemctl enable --now html-artifact-deploy
journalctl -u html-artifact-deploy -n 20

    Uvicorn reports that it is running on http://127.0.0.1:8765, with no traceback.

  12. Install the hourly purge of expired pages:
    for f in html-artifact-deploy-purge.service html-artifact-deploy-purge.timer; do
  sudo curl -fsSL -o /etc/systemd/system/$f \
    https://raw.githubusercontent.com/andras-tkcs/html-artifact-deploy/feature/publish-pages/deploy/$f
done
sudo systemctl daemon-reload
sudo systemctl enable --now html-artifact-deploy-purge.timer
sudo systemctl start html-artifact-deploy-purge.service
systemctl list-timers html-artifact-deploy-purge.timer
journalctl -u html-artifact-deploy-purge -n 5

    The timer listed with a next run within the hour, and the manual run logging Deleted 0 expired pages.

  13. Put the two sites from deploy/Caddyfile.example into /etc/caddy/Caddyfile, using your host names, then run sudo systemctl reload caddy.
  14. Check both hosts from your own machine:
    curl -s https://publish.example.com/healthz
curl -sI https://pages.example.com/

    ok, then HTTP/2 404 with content-security-policy: sandbox allow-scripts …, x-robots-tag: noindex, nofollow and no directory listing.

ma2 · claude.ai and Claude Desktop

Time about 25 minutesNeeds ma1 done, a GitHub account, a claude.ai account that can add custom connectors, and a second Google account outside your domain
  1. Open claude.ai → Settings → Connectors and choose Add custom connector. Name it Publish pages and set the URL to https://publish.example.com/mcp, then click Add and Connect.

    Google's account chooser opens. Pick your Workspace account, and you return to claude.ai with the connector marked connected. If claude.ai shows a registration error naming a redirect URI, copy that URI into the PR: the server's default allowlist needs it.

  2. In a new chat with the connector turned on, ask: "Make a one-page HTML report about our Q3 goals with a small chart, and publish it." Approve the publish_page call.

    Claude answers with a link like https://pages.example.com/3f9c0a…<32 characters 0–9 and a–f>/, with no file name or title in it, and an expiry about 90 days from today. The page opens in a private window, and its chart script runs.

  3. Ask: "Change the title to Q3 goals (draft) and republish the same page."

    The same link. After a reload the page shows the new title.

  4. Ask: "List my published pages."

    The page appears once, with its link and its expiry date.

  5. Ask: "Keep that page online for 12 months." Approve extend_page_expiry. Then ask for "13 months".

    The first answer gives an expiry about 365 days from today. The second is either refused with "days must be from 1 to 365", or Claude caps it at 365 days itself.

  6. Ask: "Take that page down." Approve unpublish_page.

    After a reload the link returns 404.

  7. Put a small HTML file in a public GitHub repository or gist, open it, and copy its Raw address (it starts with https://raw.githubusercontent.com/). In claude.ai, ask: "Publish the page at <that address> as URL test." Approve publish_page_from_url.

    A new https://pages.example.com/<id>/ link that shows the same page.

  8. Ask: "Publish the page at https://example.com/ as Refused test."

    A tool error saying the server only fetches pages from raw.githubusercontent.com, and no new page.

  9. Open Claude Desktop, signed in to the same account. The connector syncs from claude.ai. Publish one short page from Desktop and open its link.
  10. Disconnect the connector in claude.ai, then connect it again. This time pick the Google account from outside your domain.

    A page reading <address> may not publish pages on this server… (HTTP 403), and claude.ai stays disconnected. Reconnect with your Workspace account afterwards.

Report into the PR: ma2 claude.ai + Desktop: PASS, or FAIL at step N: <what you saw>.

ma3 · Claude Code: OAuth, API token and a large page

Time about 20 minutesNeeds ma1 done, Claude Code on your own machine, and SSH to the server
  1. Run claude mcp add --transport http publish-pages https://publish.example.com/mcp. Start claude, run /mcp, choose publish-pages and then Authenticate.

    A browser tab opens Google's chooser and then shows that authentication succeeded. /mcp lists the server as connected with 7 tools.

  2. Ask Claude Code to write a large single-file HTML page (over 300 KB, for example a table of 3,000 rows) to big.html, then publish it with create_page_upload.

    Claude calls create_page_upload, uploads the file with curl --upload-file big.html "<upload_url>", which prints "Uploaded … bytes", then calls publish_page with upload_id. The link opens the full table.

  3. On the server, create an API token for yourself:
    sudo systemd-run --pty --wait --uid=html-artifact-deploy -p EnvironmentFile=/etc/html-artifact-deploy/secrets.env -p StateDirectory=html-artifact-deploy \
  /opt/html-artifact-deploy/bin/html-artifact-deploy --config /etc/html-artifact-deploy/config.toml token create --user you@example.com --name laptop

    The token is printed once. Paste it only into the next command, on your own machine. Never paste it into chat or the PR.

  4. Replace the OAuth entry with the token:
    claude mcp remove publish-pages
claude mcp add --transport http publish-pages https://publish.example.com/mcp --header "Authorization: Bearer <token>"
    Start claude and ask it to publish a one-line page.

    No sign-in prompt, and a working link.

  5. Revoke the token on the server: repeat step 3's command with token revoke --user you@example.com --name laptop. Ask Claude Code to list your pages.

    The server prints Revoked., and Claude Code reports the server as unauthorized (401).
